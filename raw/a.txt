# GPT
この記事の要点は、**「モデル単体の賢さ」ではなく、モデルを長時間働かせるための外側の仕組み＝harness の設計が、成果物の質を大きく左右する**という話です。

ここでいう **harness** は、単なるプロンプトではなく、複数のエージェント、ファイルによる引き継ぎ、評価ループ、ブラウザ操作、QA、仕様分解などを組み合わせた実行環境です。

## 何を解こうとしている記事か

Anthropic の著者は、主に2つの問題に取り組んでいます。

1つ目は、Claude に良いフロントエンドデザインを作らせること。2つ目は、人間の介入なしで、数時間かけてアプリ全体を作らせることです。著者は、以前の frontend design skill や long-running coding agent harness で性能改善できたが、限界があったと述べています。そこで、GAN に着想を得て、**作るエージェントと評価するエージェントを分ける**構造を試しています。([Anthropic][1])

中心的な発想はこうです。

> 生成する者と評価する者を分ける。
> 評価基準を明示する。
> 長時間タスクは分解し、状態を構造化して引き継ぐ。
> 必要なら文脈をリセットする。
> ただし、モデルが進歩したら、その足場は削る。

## なぜ単純な実装では失敗するのか

記事は、長時間のエージェント実行でよく起きる失敗を2つ挙げています。

1つ目は、**長いタスクで一貫性が崩れること**です。コンテキストが埋まるにつれて、モデルが作業を早く畳もうとする「context anxiety」のような挙動があると説明されています。以前の harness では、コンテキストを要約して続ける compaction だけでは不十分で、完全に新しいエージェントに切り替え、構造化された handoff artifact で状態を渡す「context reset」が有効だったと述べています。([Anthropic][1])

2つ目は、**自己評価が甘いこと**です。自分で作ったものを自分で評価させると、明らかに微妙なものでも肯定的に評価しがちだ、という観察です。特にデザインのように正誤が明確でない領域では顕著です。そこで、作る agent と評価する agent を分離し、評価側を懐疑的にチューニングする方が、生成側に自己批判させるより扱いやすいとしています。([Anthropic][1])

ここはかなり重要です。
「AIに自己レビューさせればよい」では足りず、**レビュー役の人格・基準・道具・合否判定を別に設計する必要がある**という話です。

## フロントエンドデザインでの実験

まず著者は、主観的品質を評価可能にするため、フロントエンドデザインで試しています。

評価基準は4つです。

| 基準             | 見ているもの                       |
| -------------- | ---------------------------- |
| Design quality | 全体としてまとまりや雰囲気があるか            |
| Originality    | テンプレ的・AIっぽい見た目から脱しているか       |
| Craft          | タイポグラフィ、余白、色、コントラストなどの技術的完成度 |
| Functionality  | ユーザーが迷わず使えるか                 |

特に Design quality と Originality を重視したと書かれています。Claude は機能性や基本的な実装は比較的こなすが、放っておくと無難で平凡な UI に寄りやすいためです。([Anthropic][1])

実装としては、generator が HTML/CSS/JS を作り、evaluator が Playwright MCP で実際にページを操作し、スクリーンショットを見ながら採点します。その批評を generator に戻し、5〜15回ほど反復します。1回の生成に最大4時間かかったとされています。([Anthropic][1])

ここで面白いのは、評価基準の言葉自体が生成物の方向性を変えることです。たとえば “museum quality” のような語を入れると、出力が特定の美術館的な方向に収束したと述べられています。([Anthropic][1])

つまり、評価基準は単なる測定器ではなく、**生成物の価値観を規定する設計文書**でもあります。

## full-stack coding への拡張

次に、同じ構造をアプリ開発全体に拡張しています。

初期版の構成は3エージェントです。

| エージェント    | 役割                                          |
| --------- | ------------------------------------------- |
| Planner   | 短いユーザー指示を、製品仕様に展開する                         |
| Generator | 仕様に沿って、スプリント単位で実装する                         |
| Evaluator | Playwright MCP でアプリを実際に操作し、UI・API・DB状態を確認する |

Generator は React / Vite / FastAPI / SQLite、後に PostgreSQL のようなスタックで実装し、git も使います。Evaluator は見た目だけでなく、実際にクリックし、API や DB 状態も確認し、product depth / functionality / visual design / code quality のような基準で評価します。([Anthropic][1])

重要なのは、各スプリントの前に **sprint contract** を作る点です。Generator が「今回は何を作り、どう確認するか」を提案し、Evaluator がそれをレビューし、合意してから実装に入ります。通信はファイル経由で行われます。([Anthropic][1])

これは、かなり実務的な設計です。
曖昧な仕様からいきなり実装させるのではなく、**「今回の完了条件」を先にレビューさせる**ことで、あとから「それは作るべきものではなかった」という失敗を減らしています。

## 単独エージェントとの比較

実験では、「2D retro game maker」を作るタスクで、単独エージェントと full harness を比較しています。

単独実行は20分で9ドル、full harness は6時間で200ドル。コストは20倍以上ですが、品質差は明確だったとされています。単独実行では見た目はそれらしいが、実際のゲームプレイが壊れていた。一方で full harness では、16機能・10スプリントの仕様に展開され、sprite animation、behavior templates、sound/music、AI-assisted sprite generator、export なども含まれました。([Anthropic][1])

Evaluator は、たとえば「矩形塗りつぶしがドラッグ領域を埋めていない」「エンティティ削除条件が間違っている」「FastAPI のルート順序のせいで `/frames/reorder` が誤って `{frame_id}` にマッチしている」といった具体的なバグを見つけています。([Anthropic][1])

ただし、記事は QA agent が最初から優秀だったとは言っていません。むしろ、初期の Claude は QA としては甘く、正当な問題を見つけても「大したことではない」と自分で納得して通してしまった。そこでログを読み、人間の判断とズレた箇所を見つけ、QA プロンプトを何度も調整したと述べています。([Anthropic][1])

ここも大事です。
**Evaluator を置けば自動的に品質が上がるのではなく、Evaluator 自体を育てる必要がある**。

## モデルが進歩すると harness は変わる

記事後半で、Opus 4.6 の登場により harness を簡略化した話が出てきます。

初期の harness では、スプリント分解や context reset が重要でした。しかし Opus 4.6 は長いタスクをより保ち、コードレビューやデバッグ、自分のミス検出が改善されたため、以前ほど多くの足場が不要になったとしています。([Anthropic][1])

そこで著者はスプリント構造を削り、planner と evaluator は残しつつ、評価を各スプリントごとではなく終盤の数回に変更しました。DAW、つまりブラウザ上の音楽制作アプリを作る実験では、約3時間50分、124.70ドルかかっています。builder は2時間以上、スプリント分解なしで一貫して走れたとされています。([Anthropic][1])

ただし QA はまだ有用でした。DAW の例では、見た目や AI 統合は良いが、タイムライン上でクリップをドラッグできない、録音が stub-only、EQ カーブのような視覚的編集がない、といった「コア機能の未実装」を QA が指摘しています。([Anthropic][1])

結論として、Evaluator が必要かどうかは固定ではありません。
**現在のモデルが単独で安定してこなせる範囲では evaluator はコストになる。モデルの能力境界を超えるタスクでは evaluator が価値を持つ**、という整理です。([Anthropic][1])

## この記事の実践的な教訓

この記事から取り出せる実践知は、だいたい次のようになります。

### 1. エージェント開発は「モデル選び」より「外側の設計」が効く

長時間タスクでは、モデルに一発で頼むより、Planner / Generator / Evaluator のように役割を分けた方がよい場合がある。特に、仕様が曖昧で、成果物の評価に実操作が必要な場合です。

### 2. 評価基準は出力を形成する

「何を良いとするか」を明示すると、モデルはそれに沿って生成物を変えます。これはプロンプトというより、**価値観の埋め込み**です。デザイン、文章、研究、可視化、分析レポートなどでも同じことが起きるはずです。

### 3. 自己評価だけでは弱い

生成者と評価者を分けることで、評価の甘さを下げられます。ただし evaluator も LLM なので、懐疑的に、具体的に、深く検証するように調整しないと、表面的な QA になります。

### 4. 「完了条件の合意」を先に作る

sprint contract はかなり有用です。実装前に「この作業で何ができたら完了か」「どうテストするか」を generator と evaluator に合意させる。これは人間の開発でも使えます。

### 5. harness はモデル更新ごとに見直す

モデルが弱い時代に必要だった分解・リセット・監視が、新しいモデルでは不要になることがあります。逆に、新しいモデルだからこそ、より高いレベルの harness が可能になる。記事の最後では、モデルが進歩しても harness の探索空間は狭まらず、移動すると述べています。([Anthropic][1])

## 西尾さんの文脈に引きつけると

これは、以前話していた Karpathy の LLM Wiki や、Claude Code / Devin 的な長時間作業の設計とかなり近いです。

特に重要なのは、**知的作業を長時間 AI に任せるには、単に「続けて」と言うのではなく、作業環境側に記憶・分解・評価・引き継ぎ・レビューを設計する必要がある**という点です。

LLM Wiki に当てはめるなら、たとえばこういう構成になります。

| 役割               | LLM Wiki での対応                   |
| ---------------- | ------------------------------- |
| Planner          | 読むべき資料群から、Wiki 化の方針・章立て・概念地図を作る |
| Generator        | Markdown ページを作る、リンクを張る、要約・比較を書く |
| Evaluator        | 原典との対応、リンク切れ、論理の飛躍、重複、説明不足を検査する |
| Handoff artifact | 作業ログ、未解決論点、次に読むファイル、変更済みページ一覧   |
| Sprint contract  | 「この資料から何を抽出し、どのページに反映し、どう検証するか」 |

特に「AIフィードバック機能を別途必要」と話していた部分に、この evaluator の設計がそのまま入ります。人間が読書中にコメントを入れるだけでなく、そのコメントを evaluator が後で処理し、「原典確認が必要」「ページ分割すべき」「この概念は既存ページに統合すべき」のように分類できる。

ただし、この記事の方式は重いです。6時間200ドル、4時間124ドルという規模の実験なので、常用するには高コストです。現実的には、最初から full harness にするより、まずは次の最小構成がよさそうです。

1. Planner が作業単位を切る
2. Generator がファイルを編集する
3. Evaluator が差分と成果物を読む
4. 人間が evaluator の指摘だけ確認する

この4段階で十分に効果が出る可能性があります。

## 一言でまとめると

この記事は、**長時間動く AI エージェントを作る仕事は、モデルに命令する仕事ではなく、作業制度を設計する仕事である**、という話です。

そしてその制度の中核は、生成・評価・引き継ぎ・完了条件・道具使用です。
Claude Code や LLM Wiki のようなシステムを考える上では、かなり直接的に参考になる記事です。
