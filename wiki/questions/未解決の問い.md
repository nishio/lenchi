# 未解決の問い・継続課題

このプロジェクトを引き継ぐエージェントが **次に取り組むべきこと** をここに集約する。問いは大きく3層：本書の主題に関わる **理論的問い**、本書の構成に関わる **編集上の問い**、運用上の **作業課題**。

## このファイル自体の位置づけ（[Day 14](../timeline/Day14.md) で明示化）

本ファイルは LENCHI Wiki の **first-class artifact** である。3-Wiki 比較実験（[Wikiの人格化](../concepts/Wikiの人格化.md)）で確認された LENCHI の独自構造は、ingest イベントが **二層** に記録されることにある：

- **concept layer**: 新概念ページ・新エンティティページが追加される
- **question layer**（このファイル）: Q が新設・状態更新（部分対応 / 解決）される

すべての ingest / query が両層に状態変化を刻むことで、「**何が解決されたか**」「**何がまだ未決か**」を時間軸で navigable に保つ。これは「書籍プロジェクト」としての時間的な開始点と完成点を意識した設計判断であり、Karpathy の LLM Wiki や [ConnectingDots](../concepts/ConnectingDots.md) には対応する artifact がない。

### アクティブ vs アーカイブの分離（2026-05-06〜）

本ファイルには **未解決・部分対応・半解決** の問いだけを置く。**完全に解決した問い** は解決日付きで [解決済みの問い](解決済みの問い.md) に移動する。Q 番号は安定識別子として両ファイルにまたがって一意で、本ファイルに欠番（Q14・Q16・Q17）があるのは正常。

### Q3. 収束をどう支援するか
発散は LLM が得意、収束は課題（[発散と収束](../concepts/発散と収束.md)）。解候補：

1. **[KJ法とLLM](../concepts/KJ法とLLM.md)** の組み合わせ — 空間配置で人間が収束を主導
2. **[フラクタル要約](../concepts/フラクタル要約.md)** — 詳細度を選んで読む
3. **コンテキスト幅の広いモデル**（[o1 pro](../entities/o1pro.md) など）— 文脈を保持したまま長対話
4. **LLM Wiki**（[Day 12](../timeline/Day12.md) 以降の本書プロジェクト自身の運用で確認）— 概念抽出そのものが収束操作、[段階的開示](../concepts/段階的開示.md) で overview↔詳細の往復、[後段としてのWiki](../concepts/後段としてのWiki.md) が並列発散を時間をかけて吸収・収束させる。**現状もっとも有望**

それぞれを実例で示し、比較する章が未着手。LLM Wiki アプローチは本書プロジェクト自身が走る実例なので、[第二部 導入章](../chapters/第二部-LLM_Wikiの導入.md) と接続して書ける。

### Q4. [有限化と無限ネットワーク](../concepts/有限化と無限ネットワーク.md) の接続設計（**部分対応**）
書籍（有限）から、背後の [Scrapbox](../entities/Scrapbox.md)（無限）にどう橋を架けるか。本書自体がこの接続のプロトタイプになるべき。

中間層の選択肢が 2 つに分かれた：

- **B. Claude Code + LLM Wiki** — [Day 12](../timeline/Day12.md) 以降。**[段階的開示](../concepts/段階的開示.md) 型**の構造化された記憶＋エージェント。「特化した記憶を持って話し相手になる」という NISHIO アシスタントの中核機能を、Naive RAG ではなく Wiki 経由で実現する。収束側の支援も強い（[Q3](#q3-収束をどう支援するか)）。

残課題：

- 本書で読者に提示する入口は **B のみ** にするのか、サービス提供論を本論で扱うのか。
- 「最新サブスクを払う」前提を本書がどこで開示するか（[Q15](#q15-人間--ai-の協働前提の妥当性) と関連）。

### Q5. 価値あるアイデアとは何か
講演・第一章で「アイデアを思いつく」プロセスが重要であると述べたが、**価値あるアイデアの判断基準** は深掘りされていない。「実行されないアイデアに価値はなく、実現不可能なアイデアにも価値はない」という著者のメモ（[Day1](../timeline/Day1.md)）からの発展が必要。

**[2026-05-07] 著者見解**（`raw/2026-05-07-nishio-Q4Q5コメント.txt` から ingest）:

アイデアの実現には **抽象的なアイデアを実行可能なネクストアクションにまで噛み砕く** 作業が必要。LLM 時代の構造変化：

- **分解作業（抽象→ネクストアクション）は AI 支援で大幅に容易化**。これまで人間がやっていた認知負荷の高い橋渡しが軽減された。
- **ボトルネックは AI ではなく人間がやるしかないアクションの実行に移った**。それが行われるかどうかは、人間の **可処分時間** と **精神的キャパシティ** に依存する。
- → これは [Q25](#q25-プロジェクトが進まない問題)（プロジェクトが進まない問題）と直結。停滞の所在が「分解できない」から「実行リソースが足りない」に移った、という診断。

残課題：

- 「価値ある」の判断基準そのものは依然として未深掘り。実行可能性という閾値は、AI 支援で緩和された。
- 本書で「アイデアの実行可能性への分解」を独立したスキル／節として扱うかどうか。

### Q24. 記憶問題は想起の設計問題である
[Q1](#q1-llm-時代に普遍適応の境界はどこか) の「記憶」サブトピックの再フレーミング（[Day 15](../timeline/Day15.md)）。

著者の見立て：

> 雑に言えば、記憶は人間だけでなく LLM も持つようになった、それが LLM Wiki の形で整理されている。「記憶」の消えずに保存する側面は遥か昔から実現されていた。紙の本もそうだ。**重要なのは想起の部分** である。**どのような形で保存すればより良く想起できるのか** が重要。

含意：

- 保存（passive storage）は紙の本・データベース・LLM パラメータ内記憶など多様な形で **既に解決済み**。
- 残る問題は **想起の設計**: どの形式で保存すれば、必要な時に必要な部分が必要な形で取り出せるか。
- LENCHI 第二部の中核概念群（[後段としてのWiki](../concepts/後段としてのWiki.md)・[段階的開示](../concepts/段階的開示.md)・[ナラティブの価値](../concepts/ナラティブの価値.md)・[RAG](../concepts/RAG.md) の Naive RAG 反省）は、すべて **想起の設計** を扱っている。Q1 の「記憶」は本書の主題そのものだったが、当初は古い枠（人間記憶論）で問われていた。
- 詳細は新規概念ページ [想起の設計](../concepts/想起の設計.md) を参照。

本書での扱い：第一章 / 前書きで「記憶」を扱う際、**「保存ではなく想起の設計」** という枠で書き直す候補。

### Q25. プロジェクトが進まない問題（「やる気」概念の解体）
[Q1](#q1-llm-時代に普遍適応の境界はどこか) の「やる気」サブトピックの再フレーミング（[Day 15](../timeline/Day15.md)）。

著者の見立て：

> やる気は、目的が明確でないときや、目的のために進む道が見えないときに失われる。やる気とか MP などの概念で解釈すること自体が不適切かもしれない。「**何らかの理由でプロジェクトが先に進んでいかないとき**」にどう解決するかの揉んだ問いにした方がいいだろう。**プロジェクトを遂行するのが人間とは限らない** 時代でもある。

含意：

- 「やる気」「MP」は人間の心理状態を擬似的に資源として扱うメタファーで、原因（目的不明確 / 道筋不可視）を隠してしまう。
- 真の問いは **プロジェクトの停滞メカニズム** の解明と解消手段。停滞要因の主なクラス：
  - 目的が言語化されていない
  - 目的への道筋が見えていない（**抽象→ネクストアクション分解の失敗**、[Q5](#q5-価値あるアイデアとは何か) と接続）
  - 認知負荷が局所に集中している（[後段としてのWiki](../concepts/後段としてのWiki.md) で部分的に解決可能）
  - 進捗が観測できない（メタ認知の支援不足）
  - **人間にしかできないアクションの実行リソース不足**（可処分時間・精神的キャパシティ。Q5 の著者見解からの追加、2026-05-07）
- **遂行主体の一般化**: LLM 時代には、エージェントや人間 + AI 混合チームがプロジェクトを進める場面が増える。「やる気」概念は人間にしか適用できないが、停滞の物理は主体非依存。
- **ボトルネックの移動**: 抽象→具体の分解は AI 支援で軽くなった。停滞の所在は「分解できない」から「実行リソースが足りない」に移っている（→ [Q5](#q5-価値あるアイデアとは何か) 著者見解）。
- LENCHI 自身が 17 か月中断（[Day 11](../timeline/Day11.md)）した経験は、この問いの直接的な事例（→ [overview.md](../overview.md) の「プロジェクトの性格」）。

### Q26. AI が同一ファイルを編集中に人間が割り込みコメントしたいときどうするか
[2026-05-07] に著者が Q4・Q5 を直筆更新した際、LLM が同一ファイルを編集している最中だったため **IDE での同時編集衝突** が発生した。一時的に `nishio:` プレフィックスを行頭に付ける運用で乗り切ったが、**運用問題（merge conflict）はファイル内記法では解決できない** と判断。

**今回の処理**: 該当コメントは `raw/2026-05-07-nishio-Q4Q5コメント.txt` に移動し、Wiki は AI 生成テキストのみの状態に復元（Wiki と raw の 3 層分離原則の遵守）。

未決：

- AI 作業中に人間がコメントしたくなった場合、**どこに書くのが適切か**？
- 候補：
  - **`FEEDBACK.md` 様の専用ファイル** — グローバル CLAUDE.md には既にこの慣習がある（人間メモ専用、AI は明示的指示があるまで読まない）。LENCHI でも採用するか
  - **`raw/` への直接書き込み** — 今回採用した処理。raw は人間の生コメントの自然な置き場所
  - **チャットで言うだけ** — Wiki に持ち込まず、AI が次のセッションで反映する
  - **handoff プロトコル** — AI が一旦 commit して停止、人間が編集、AI が再読してから次の作業
  - **branch-and-merge** — 機械的衝突を git で解決

設計上の論点：

- **割り込みの即時性 vs 衝突回避** のトレードオフ
- **anti-misattribution 規律**（誰の発言かを保つ）は別途必要だが、ファイル内記法に頼らない解で実現する必要
- 今回の処理（raw 化）は **「人間の生コメント = raw」** という 3 層原則の自然な拡張であり、有力候補
