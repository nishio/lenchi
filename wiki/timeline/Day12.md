### Q16 の検証結果（要約）

#### 概ね妥当な点

- Karpathy の LLM Wiki が改善したのは LLM の **内部記憶そのもの** ではなく、「**会話履歴に詰め込む問題から、LLM が読み書きできる外部 Markdown 知識体系を保守・検索する問題へ移すこと**」である。
- 単一手法の発明というより、長文コンテキスト・tool use・filesystem access・agentic memory・progressive disclosure・Claude Code 的作業環境の **成熟が重なった** 結果として有用性が上がった。
- これは研究系譜（RAG → ReAct → Reflexion → MemGPT → Generative Agents → Voyager → A-MEM、および LLM agent memory のサーベイ）からも傍証が得られる。

#### 訂正された点

著者の元見立て「**Claude Code の Skills が早期形態**」は **半分正しい**。より正確には：

- **Skills は手続き知識・作業手順の外部化**が中心。LLM Wiki は **意味知識・出典付き統合知識の外部化** が中心で、目的物が違う。
- ただし「必要時だけ読む progressive disclosure」という設計原理は強く対応している。
- **Claude Code 全体（Skills + CLAUDE.md + auto memory + memory tool + filesystem access）** をまとめて見れば、LLM Wiki にかなり近い先行形と言える。

#### タイムラインの訂正

著者の元発言には「auto memory や memory tool は Skills の後では？」という自己疑問もあり、これは GPT 側の最初の整理が雑だった点。サーベイで確定した順序：

| 時期         | 出来事                                                                 |
| ---------- | ------------------------------------------------------------------- |
| 2024-11-25 | Anthropic MCP 発表（外部システム接続の基盤）                                       |
| 2025-02-24 | Claude Code research preview                                        |
| **2025-09-29** | **API memory tool beta**（Skills より前）                                |
| **2025-10-16** | **Agent Skills / Claude Code Skills**                               |
| **2026-02-05** | **Claude Code auto memory** の初期記述（Skills より後）                       |
| 2026-02-26 | auto-memory が明示化（`/memory` で管理）                                     |
| 2026-03-12 | `autoMemoryDirectory` 設定追加                                          |

→ 「**API memory tool は Skills より少し前、Claude Code 内の auto memory は Skills より後**」と用語を区別する必要がある。

#### 著者の追加観察（filesystem access）

著者は 2 ラウンド目で次の重要観察を投げた：

> filesystem access の進歩が「ファイルを普通に置いといて普通のツールで検索する」という振る舞いを生んだ。これは特に **ソースコードがファイルシステム上に構造化されて配置されたものであった** ことによって需要があった。

GPT も追認：ソースコードはもともとディレクトリ・命名・import・README・テスト・設定・Git 履歴・エラーログという「探索可能な外部記憶」を持っており、Claude Code が `grep`/`glob`/`read`/`bash` で扱う運用を **既存の道具** で実現できた。文書知識管理（LLM Wiki）も Markdown + ディレクトリへ寄せることで同じ恩恵を受ける。

→ [段階的開示](../concepts/段階的開示.md) の「ファイルシステムが事実上のインデックスになった話」節として記録。

#### 進化の系譜キーワード — Progressive Disclosure

3 ラウンド目に著者が「progressive disclosure というキーワードは大事」と指摘し、その系譜を聞いた。GPT は次の流れを整理：

- **HCI 起源**: Jakob Nielsen (2006)、Shneiderman の "overview first, zoom and filter, then details-on-demand"、Shopify Polaris の IA ガイド。
- **LLM への転用**: Skills (Anthropic, 2025-10) と Codex Skills (OpenAI) が明示的に採用。Tool Search も同型。
- **LLM Wiki**: Karpathy が長期知識管理に転用した形。

→ 独立した概念ページ [段階的開示](../concepts/段階的開示.md) として切り出し。

#### Naive RAG のバックラッシュ

著者は最後に「ベクトル埋め込み検索のバックラッシュ」に言及。GPT は次の整理：

- バックラッシュは **embedding 検索そのものへの否定ではなく、Naive RAG（固定長チャンク + embedding + top-k）への反発**。
- 失われていたもの: チャンクが文脈を失う、意味的類似 ≠ 根拠一致、top-k が「使える順」ではない、固定長チャンクで構造を破壊する。
- 反省後の実務: BM25 + vector のハイブリッド、reranking、文書構造尊重、metadata、agentic retrieval、**段階的開示**。
- Anthropic の **Contextual Retrieval**（チャンクに短い文脈説明を付けて embedding する）は典型的な反省例。実験で top-20 retrieval failure rate を 35〜49% 削減と報告。

→ [RAG](../concepts/RAG.md) ページに反映。

### 重要な発見 — ナラティブの価値が LENCHI の二層設計を事後的に正当化する

`ナラティブの価値` ページ（西尾の Scrapbox、2026-04-27 作成、本日 2026-05-02 更新）は、tokoroten による「**ブロードリスニング本Wiki でナラティブが抜けたら旨味が消えた**」というフィードバックから生まれたメタ考察。6 次元の整理は次の通り：

| 次元 | wiki 化で残るか |
| --- | --- |
| 1. 暗黙知 | ✗ |
| 2. 順序の意味 | ✗ |
| 3. 動機・現場の混乱 | △ |
| 4. 記憶への定着 | △ |
| 5. 共感・視点 | ✗ |
| 6. 意味の生成 | △ |

**wiki 化は 6 軸のうち 4〜5 軸を犠牲にして「参照可能性」を得る変換**。だからこそ、

- **`raw/`（改変禁止）** がナラティブを保存し、
- **`wiki/`** が概念抽出と参照可能性を担う、

という二層分離が必要になる。これは LENCHI の [CLAUDE.md](../../CLAUDE.md) で当初から定義されている運用方針だが、**理論的根拠が事後的に与えられた** 形である。

この発見は [第二部 導入章](../chapters/第二部-LLM_Wikiの導入.md) に「ナラティブの価値と二層分離」節として組み込む価値がある。Karpathy の LLM Wiki への重要な批評的補足になる。
