# NISHIO Hirokazu's Assistant（カスタムGPT）

[西尾泰和](西尾泰和.md) が ChatGPT のカスタム GPT として公開した **個人アシスタント**。著者の [Scrapbox](Scrapbox.md) 約2万記事と、『[エンジニアの知的生産術](エンジニアの知的生産術2018.md)』『[コーディングを支える技術](コーディングを支える技術2013.md)』のテキストをベクトル化して [RAG](../concepts/RAG.md) で参照する。

## プロジェクトでの役割

- 著者自身のブレインストーミング相手。
- 第三者が著者の知識ベースに問い合わせるインターフェース。
- 講演（Day9）でも紹介された主要事例。

## 観察された特徴

- 検索結果を毎回コンテキストに流し込むため、長い対話で **過去の発言を忘れて脱線** する傾向（[コンテキスト維持](../concepts/コンテキスト維持.md)）。
- 一方で、その「脱線」が予期せぬ視点（例：講演テーマを「学び方」と解釈し『コーディングを支える技術』の3つの学び方と接続する）を生むという、発散側の価値もある（[脱線のメリット](../concepts/脱線のメリット.md)）。

## 別実装としての Claude Code + LLM Wiki（[Day 12](../timeline/Day12.md) 以降の発見）

「**著者の知識ベースに特化した記憶を持って話し相手になる**」という本アシスタントの中核機能は、2026 年現在 **Claude Code + [LLM Wiki](../../llm-wiki.md)** によっても実現可能になった。両者は同じ機能の **別実装** である：

| | NISHIO アシスタント（2024〜） | Claude Code + LLM Wiki（2026〜） |
| --- | --- | --- |
| 記憶の形式 | Scrapbox を埋め込みベクトル化 | `raw/` + `wiki/` の Markdown 体系 |
| 検索方式 | 質問 embedding と top-k | `grep`/`glob`/`read` + `index.md` から [段階的開示](../concepts/段階的開示.md) |
| 収束支援 | 弱い（文脈を毎回流入させて脱線） | 強い（[Q3](../questions/未解決の問い.md) の現状最有望候補） |
| 発散支援 | 強い（[脱線のメリット](../concepts/脱線のメリット.md)） | 上流の並列発散を吸収（[後段としてのWiki](../concepts/後段としてのWiki.md)） |
| 第三者からのアクセス | ChatGPT カスタム GPT として一般公開 | リポジトリを公開すれば同等可能 |
| 対応する RAG パラダイム | Naive RAG | Modern RAG / agentic retrieval（[RAG](../concepts/RAG.md) のバックラッシュ後の景色） |

これは [Day 12 Session B](../timeline/Day12.md) で整理した「Naive RAG → Modern RAG」の構造変化が、個人知識アシスタントの設計にもそのまま当てはまる構図である。

含意：

- NISHIO アシスタントは **発散用の窓口** として今でも価値がある（特に第三者からのアクセス入口として）。
- 著者自身の知的生産パートナーとしては **Claude Code + LLM Wiki が主役** に移行しつつある。
- [Q4](../questions/未解決の問い.md)（[有限化と無限ネットワーク](../concepts/有限化と無限ネットワーク.md) の接続設計）では、書籍 → Wiki → raw → Scrapbox の多段橋を設計するか、A/B の両方を入口として提示するかが論点。
