# RAG（Retrieval-Augmented Generation）

汎用 LLM に **個人または組織の知識ベースからの検索結果** を組み合わせ、より具体的・文脈的な応答を生成する技術。著者にとっての RAG の意義は「**コモディティ化を回避し、自分固有のデータと汎用LLMを組み合わせて固有の価値を作る**」点にある。

## 来歴

- [Day6](../timeline/Day6.md)（2024-05-12）に著者が、自身の Scrapbox を埋め込みベクトル検索する **カスタムGPT** をリリース。原文ページ: `LENCHI_Day6`、`NISHIO Hirokazu's Assistant`（[NISHIOアシスタント](../entities/NISHIOアシスタント.md)）。

## 著者の実装

- 7年蓄積、約2万記事の Scrapbox（と『エンジニアの知的生産術』『コーディングを支える技術』のテキスト）をベクトル化。
- ChatGPT のカスタム GPT として公開し、誰でも著者の知識ベースに問い合わせ可能。
- 講演資料でも紹介された主要事例。

## 観察された限界

- GPT-4 のコンテキストサイズ制約により、再検索のたびに過去の発言を忘れて **脱線** する傾向（[コンテキスト維持](コンテキスト維持.md)）。
- 表面的にはユーザーから見えないが、内部で大量の検索結果がコンテキストに流入し、人格が一定でないように見える。

## Naive RAG とそのバックラッシュ（[Day 12 Session B](../timeline/Day12.md) 追記）

2023 年前後に「**文書を固定長チャンクに切る → embedding → vector DB → top-k 取得 → LLM に渡す**」という素朴な定式化が RAG の標準形のように扱われた。その後バックラッシュが起きたが、対象は **embedding 検索そのものではなく、この素朴な定式化（Naive RAG）への反発** だった、というのが現在の整理である。

### 何がうまくいかなかったか

1. **チャンクが文脈を失う** — 「売上は前四半期比で3%増加した」というチャンクだけ取り出しても、どの会社・どの四半期かが消える。
2. **意味的類似度 ≠ 根拠の一致** — 型番、金額、エラーコード、関数名、固有名詞のような「その文字列があること」が重要な場合に、ベクトル検索は外す。
3. **top-k 近傍は「使える順」ではない** — 似ている断片、重複、古い断片、文脈を欠いた断片が混ざる。
4. **固定長チャンク化はインデックス時点で構造を破壊する** — 見出し・章立て・表・コードのスコープ・話題遷移などが点群に変換される。

### 反省後の実務的な修正

| 素朴なRAG           | 反省後の設計                                                      |
| ---------------- | ----------------------------------------------------------- |
| 固定長チャンク          | 文書構造、見出し、表、コード単位、話題単位を尊重                                    |
| vector search のみ | BM25 / 全文検索 + vector search のハイブリッド                         |
| top-k をそのまま投入    | reranking、重複除去、context compression                          |
| チャンク単体を embedding | チャンクに文書内文脈、タイトル、metadata を付与（Anthropic **Contextual Retrieval**） |
| 黒箱の vector DB    | grep、glob、SQL、metadata filter、filesystem、knowledge graph も併用 |
| 一回検索             | query rewrite、multi-query、反復検索、agentic retrieval            |
| 検索精度を感覚で評価       | retrieval eval、answer eval、failure analysis                 |

Anthropic の **Contextual Retrieval**（2024）は典型的な反省例。チャンクごとに短い文脈説明を付けてから embedding と BM25 index を作ることで、top-20 retrieval failure rate を 35〜49% 削減と報告している。

### LLM Wiki / Claude Code 的アプローチとの関係

このバックラッシュ後の景色からは、[LLM Wiki](../../llm-wiki.md) や Claude Code 的な「**人間にも LLM にも読める構造化された知識をファイルシステムに置き、必要に応じて grep / glob / read で深掘りする**」運用が自然に立ち上がる。Naive RAG の **平坦なインデックス** と対比すると、これは [段階的開示](段階的開示.md) を備えた **多段インデックス** である：

> コーパス全体の目次 → 文書一覧 → 文書ごとの要約・見出し・metadata → 関連セクション → 原文チャンク → 必要なら周辺文脈や一次ソース

ベクトル検索は **その中の一部品** であって、中心原理ではなくなった、というのが現在の整理。[著者の RAG 実装](../entities/NISHIOアシスタント.md) も、純粋な Naive RAG というより、人間が運用する Scrapbox の構造（リンク・ハッシュタグ・括弧記法）の上にベクトル検索を被せた形であり、同じ方向の設計と言える。
