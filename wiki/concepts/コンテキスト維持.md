# コンテキスト維持

長期にわたる知的生産プロジェクトを、コンテキスト窓有限の LLM と一緒に進めるために、**プロジェクトの目的・前提・既出の合意** を外部化・要約・受け渡しする技法。

## 来歴

- [Day1](../timeline/Day1.md) で「次の LLM に引き継ぐためには何を渡せば良いか」を整理する習慣が確立。各 [Day振り返り](../timeline/) は本質的に**引き継ぎ資料**。
- [Day2](../timeline/Day2.md) でコンテキスト圧迫による「前の内容忘却」エラーが発生し、文脈管理の重要性が痛感された。
- [Day6](../timeline/Day6.md) で「**カスタムGPTとの脱線会話を別インスタンスで要約してから戻す**」という二段構えの実験。

## 鍵になる実践（2024 年の場当たり的対策）

1. **引き継ぎ資料テンプレート**: 「本のコンセプト」「目的・問題意識」「これまでの進捗」「重要概念」「次にやること」を毎日末に整理する。各 Day振り返り を参照。
2. **モデル使い分け**: 文脈維持が大事な収束フェーズはコンテキスト窓の広い [Claude 3 Opus](../entities/Claude3Opus.md) や [o1 pro](../entities/o1pro.md)、発散はカスタムGPT（[NISHIOアシスタント](../entities/NISHIOアシスタント.md)）。
3. **要約の中継**: 会話ログを別インスタンスで要約させてから、本体の対話に戻す。

これらはすべて **その場限り** の処置で、長期プロジェクトをまたいで蓄積はされなかった。

## 構造解 — LLM Wiki の導入（2026-05-01〜）

[Day 11](../timeline/Day11.md) で本プロジェクトに導入された **LLM Wiki**（[第二部 導入章](../chapters/第二部-LLM_Wikiの導入.md)）が、この概念に対する構造的な解として位置づけられた。Wiki は raw / wiki / schema の3層を分離し、LLM が編集者として **永続的に** 文脈を維持する。引き継ぎ資料は毎回作るのではなく、Wiki そのものに置き換わる。すなわち、上記実践 1〜3 は **Wiki 運用に統合された**。

これにより、本概念の中心問題（コンテキストが揮発する）は当面解決された。残る問題は「Wiki が大きくなった時に LLM 自身がどう要約・索引するか」のスケール課題に移る（[未解決の問い](../questions/未解決の問い.md) Q11）。
