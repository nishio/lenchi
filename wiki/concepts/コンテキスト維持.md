# コンテキスト維持

長期にわたる知的生産プロジェクトを、コンテキスト窓有限の LLM と一緒に進めるために、**プロジェクトの目的・前提・既出の合意** を外部化・要約・受け渡しする技法。

## 来歴

- [Day1](../timeline/Day1.md) で「次の LLM に引き継ぐためには何を渡せば良いか」を整理する習慣が確立。各 [Day振り返り](../timeline/) は本質的に**引き継ぎ資料**。
- [Day2](../timeline/Day2.md) でコンテキスト圧迫による「前の内容忘却」エラーが発生し、文脈管理の重要性が痛感された。
- [Day6](../timeline/Day6.md) で「**カスタムGPTとの脱線会話を別インスタンスで要約してから戻す**」という二段構えの実験。

## 鍵になる実践（2024 年の場当たり的対策）

1. **引き継ぎ資料テンプレート**: 「本のコンセプト」「目的・問題意識」「これまでの進捗」「重要概念」「次にやること」を毎日末に整理する。各 Day振り返り を参照。
2. **モデル使い分け**: 文脈維持が大事な収束フェーズはコンテキスト窓の広い [Claude 3 Opus](../entities/Claude3Opus.md) や [o1 pro](../entities/o1pro.md)、発散はカスタムGPT（[NISHIOアシスタント](../entities/NISHIOアシスタント.md)）。
3. **要約の中継**: 会話ログを別インスタンスで要約させてから、本体の対話に戻す。

これらはすべて **その場限り** の処置で、長期プロジェクトをまたいで蓄積はされなかった。

## 構造解 — LLM Wiki の導入（2026-05-01〜）

[Day 11](../timeline/Day11.md) で本プロジェクトに導入された **LLM Wiki**（[第二部 導入章](../chapters/第二部-LLM_Wikiの導入.md)）が、この概念に対する構造的な解として位置づけられた。Wiki は raw / wiki / schema の3層を分離し、LLM が編集者として **永続的に** 文脈を維持する。引き継ぎ資料は毎回作るのではなく、Wiki そのものに置き換わる。すなわち、上記実践 1〜3 は **Wiki 運用に統合された**。

これにより、本概念の中心問題（コンテキストが揮発する）は当面解決された。残る問題は「Wiki が大きくなった時に LLM 自身がどう要約・索引するか」のスケール課題に移る（[未解決の問い](../questions/未解決の問い.md) Q11）。

### Karpathy の貢献の位置づけ（[Day 12](../timeline/Day12.md) Session A で提起、Session B で検証）

著者の見立て：**Karpathy の LLM Wiki は単発の発明ではない**。LLM が賢くなったこととコンテキスト幅が広くなったことによって、**ある種のやり方の有用性がジワジワと上がってきた** ものを言語化したと認識するのが適切である。

[Day 12 Session B](../timeline/Day12.md) に [GPT-5 系](../entities/GPT-5系.md) でサーベイ検証した結果、この見立ては **概ね妥当（条件付き）** で確定した：

- LLM Wiki が改善したのは LLM の **内部記憶そのもの** ではなく、コンテキスト維持を「**会話履歴に詰め込む問題から、LLM が読み書きできる外部 Markdown 知識体系を保守・検索する問題へ移すこと**」である。
- 単一手法の発明というより、**長文コンテキスト・tool use・filesystem access・agentic memory・[段階的開示](段階的開示.md)・Claude Code 的作業環境** の成熟が重なった結果。
- 研究系譜（RAG → ReAct → Reflexion → MemGPT → Generative Agents → Voyager → A-MEM、および LLM agent memory のサーベイ）からも傍証が得られる。

著者の補助仮説「**Claude Code Skills が早期形態**」は **半分正しい**：

- Skills は手続き知識・作業手順の外部化が中心。LLM Wiki は意味知識・出典付き統合知識の外部化が中心で、目的物が違う。
- ただし「必要時だけ読む [段階的開示](段階的開示.md)」という設計原理は強く対応している。
- **Claude Code 全体（Skills + CLAUDE.md + auto memory + memory tool + filesystem access）** をまとめて見れば、LLM Wiki にかなり近い先行形と言える。
- 時系列の訂正：API memory tool（2025-09-29）は Skills（2025-10-16）より少し**前**、Claude Code 内の auto memory（2026-02-05〜）は Skills より**後**。「memory tool」と「auto memory」は別物として扱う。

### 並列実行への展開（[Day 12](../timeline/Day12.md)）

Wiki が後段にあるという前提が成立すると、上流の探索を並列化できる。出力をその場で理解する必要がなくなるため、複数の探索を同時に走らせても認知キャパを溢れさせずに済む。これは [後段としてのWiki](後段としてのWiki.md) として概念化した。コンテキスト維持と並列実行は、Wiki を介して相互に支え合う。
