# 段階的開示（Progressive Disclosure）

最初は **発見可能性を保ったまま、読む量を最小化する** インデックスを置き、必要になった時に深い情報を読みに行く設計原理。HCI／情報可視化の古い概念が、LLM エージェントの外部記憶設計に転用された結果、**[LLM Wiki](../../llm-wiki.md) や Claude Code Skills の中核設計** として再定式化された。

## 系譜

### UI／HCI起源
- **Jakob Nielsen (2006)** — UI 設計原理として「初期画面に重要な選択肢だけを出し、高度な選択肢や詳細情報は要求された時に開示する」と整理。
- **Ben Shneiderman の Information Seeking Mantra** — "**overview first, zoom and filter, then details-on-demand**"。情報可視化の指針として広く引用される。
- **Shopify Polaris の IA ガイド** など、現代の情報アーキテクチャでも標準的な推奨。

人間向け UI の設計原理として 20 年以上の蓄積がある。

### LLM への転用
- **Naive RAG** （文書を固定長チャンクに切る → embedding → top-k 取得）は事実上 **平坦なインデックス** で、上位概念や隣接情報が見えない。これへの反省（[RAG](RAG.md)）が、多段インデックスの必要性を浮上させた。
- **Anthropic の Agent Skills**（2025-10-16 公開）が、`name/description`（常時ロード）→ `SKILL.md`（必要時）→ `resources/scripts`（さらに必要時）という三段階の開示を **明示的に "progressive disclosure"** と命名して採用。
- **OpenAI Codex Skills** も同じパターンを採る。**Tool Search**（namespace と server description を先に見せ、必要なツールだけロード）も同型。Anthropic 固有のアイデアではなく **LLM エージェント設計全体に広がったパターン**。
- **Karpathy の [LLM Wiki](../../llm-wiki.md)**（2025）は、この原理を **長期知識管理** に適用したものと位置づけられる。schema/index → wiki ページ → raw sources の三層構造は典型的な多段インデックス。

### 隣接系譜（外部記憶の歴史）
- **RAG (Lewis et al., 2020)** — モデル内パラメータ記憶の限界を、外部の非パラメトリック記憶（Wikipedia 等）の検索で補う。
- **ReAct (Yao et al., 2022)** — 推論と外部行動の交互実行。
- **Reflexion (Shinn et al., 2023)** — 反省を episodic memory として保持し再利用。
- **Generative Agents (Park et al., 2023)** — memory stream を関連性・新しさ・重要度で動的取り出し。
- **MemGPT (Packer et al., 2023)** — 階層メモリを LLM 自身に管理させる OS 的アーキテクチャ。
- **Voyager (Wang et al., 2023)** — 増え続ける skill library として獲得行動を保存・検索。
- **A-MEM (2025)** — Zettelkasten 的な動的インデックスとリンクで agentic memory を構成。

## 本書プロジェクトでの含意

LENCHI Wiki の運用（[CLAUDE.md](../../CLAUDE.md) で定義）は段階的開示の典型例である：

- **常時ロード**: `CLAUDE.md`（スキーマ）、`overview.md`、`index.md` だけが入口情報として常に読まれる。
- **必要時ロード**: 各 `concepts/`, `entities/`, `chapters/`, `timeline/` ページは、index で関連と判断されたときだけ読む。
- **最深層**: `raw/` は wiki ページから根拠が必要なときだけ参照する。

[フラクタル要約](フラクタル要約.md) も段階的開示の実例である。Shneiderman の "overview → zoom → details" を要約システムに適用したものと言える。

## なぜ「全部入れる」では足りないのか

長コンテキストモデルが普及しても、段階的開示は廃れない。**Lost in the Middle**（Liu et al., 2023）が示したように、文脈の中央にある情報は性能劣化を起こす。**RULER** などの評価も、needle-in-a-haystack 型の単純評価だけでは長文理解を測れないと論じる。Anthropic の "Effective context engineering for AI agents" は、コンテキストを **有限資源** と捉え、just-in-time retrieval、compaction、note-taking、memory tool を組み合わせるべきと整理する。

すなわち、コンテキスト幅の拡大は **段階的開示を不要にしない**。むしろ「何を入れるか」を選ぶための上位インデックスの重要性が増す。

## ファイルシステムが事実上のインデックスになった話

[Day 12 Session B](../timeline/Day12.md) で著者が指摘したのは、**ソースコードがそもそもファイルシステム上に構造化されていた** ことが、段階的開示型の外部記憶を一気に実用化した、という観察である。

リポジトリにはディレクトリ、命名、import、README、テスト、設定、Git 履歴、エラーログがあり、これらはすでに「探索可能な外部記憶」として機能していた。Claude Code が `grep`/`glob`/`read`/`bash` で必要時に探索するスタイルを **既存の道具** で実現できたのは、ソースコード領域がこの構造を先に持っていたからである。文書知識管理（LLM Wiki）も、Markdown + ディレクトリという同じ形式に寄せることで、同じ恩恵を受ける。
